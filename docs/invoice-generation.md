# Счёт PDF при создании заказа

При `POST /api/orders` сервер заново проверяет товары и суммы по каталогу,
формирует PDF для оплаты по счёту и сохраняет заказ вместе с готовым документом.
PDF содержит реквизиты поставщика и покупателя, товарные строки, итог, НДС,
бесплатную доставку и сумму прописью. Измеряемые товары выставляются в тоннах
по цене за тонну; длина указана дополнительно. Денежные суммы совпадают с заказом.

## Текущий режим: образец

По запросу владельца сайта банковский счёт и ставка НДС пока заменены заглушками
на красном фоне. У документа есть надпись «Образец - не для оплаты».
НДС включён в цены; доставка бесплатная. Номер из прежних реквизитов
`4070281080000020353` содержит 19 цифр и не используется как платёжный реквизит.

По умолчанию действует `INVOICE_MODE=preview`. Образец также можно скачать
со страницы подтверждения. Если SMTP подключён, письмо явно сообщает, что это
образец, который нельзя оплачивать.

Для выпуска платёжных документов задайте:

```dotenv
INVOICE_MODE=live
INVOICE_BANK_ACCOUNT=<подтверждённый 20-значный расчётный счёт>
INVOICE_VAT_RATE=<подтверждённая ставка: 5, 7, 10 или 22; NONE для без НДС>
INVOICE_PRICES_INCLUDE_VAT=true
INVOICE_PAYMENT_DAYS=3
```

Режим `live` проверяет длину и контрольную сумму банковского счёта относительно
БИК из `lib/companyDetails.ts`, ставку и включение НДС в цены. Неверная настройка
останавливает создание нового заказа до сохранения и отправки письма. Контрольная
сумма не подтверждает принадлежность счёта организации: нужны банковские реквизиты.
Три календарных дня для оплаты - настраиваемое значение шаблона.

## Скачивание и хранение

Кнопка «Скачать счёт PDF» запрашивает
`GET /api/orders/[reference]/invoice` с отдельным случайным токеном в заголовке
`Authorization: Bearer …`. Токен не попадает в URL. Номер заказа сам по себе
не даёт доступа к документу. Сервер хранит хеш токена. Ответы содержат
`Cache-Control: private, no-store`; PDF не размещается в `public/`.

Токен сохраняется в `sessionStorage` вместе с подтверждением заказа. При
заблокированном хранилище доступна память текущей вкладки. После закрытия вкладки
для покупателя остаётся PDF из письма; личного кабинета и восстановления доступа
по номеру заказа в этой реализации нет.

PDF сохраняется в заказе в Base64. Повторное скачивание отдаёт те же байты;
изменение каталога, реквизитов, налоговой настройки или шаблона старый документ
не меняет. Образец, созданный до настройки реквизитов, остаётся образцом.

В development файлы заказов находятся в игнорируемом `.local/orders`.
В production обязательно задайте `ORDER_STORAGE_DIR` абсолютным путём на приватном
постоянном диске. Каталог в `public/` запрещён. Файлы публикуются атомарно,
имеют права `0600`, новые заказы не перезаписывают существующие. Обновления
статусов сериализуются внутри экземпляра репозитория.

Файловый адаптер рассчитан на один Node-процесс и постоянный диск. Для нескольких
процессов/реплик или serverless нужен общий транзакционный адаптер `OrderRepository`.
Произвольный временный каталог не заменяет постоянное хранилище. Заказы содержат
персональные данные: доступ к каталогу и резервным копиям должен быть ограничен.

## Почта

SMTP-адаптер Nodemailer отправляет покупателю письмо с сохранённым PDF во вложении,
копия менеджеру - BCC. Используются серверные переменные из `.env.example`:

```dotenv
NOTIFICATION_PROVIDER=smtp
NOTIFICATION_RECIPIENT_EMAIL=<email менеджера>
SMTP_HOST=<SMTP сервер>
SMTP_PORT=465
SMTP_USER=<логин>
SMTP_PASSWORD=<пароль приложения или SMTP пароль>
SMTP_FROM=<подтверждённый адрес отправителя>
```

Порт 465 использует TLS; остальные порты требуют STARTTLS (обычно 587).
Загрузка вложений по URL и произвольным файловым путям отключена.
Секреты нельзя добавлять в Git или в переменные `NEXT_PUBLIC_*`.

Сбой формирования PDF или сохранения заказа возвращает 503 без отправки письма.
Если заказ уже сохранён, почтовый сбой не отменяет его: API возвращает 201,
`invoice.emailStatus=FAILED`, а страница предлагает скачать PDF и сообщает,
что повторно создавать заказ не нужно. `SENT` означает принятие письма SMTP-сервером
для адреса покупателя, а не подтверждённую доставку в почтовый ящик.
Автоматическая очередь повторных попыток в этой реализации не подключена.
После сбоя отправки PDF остаётся в сохранённом заказе.

## Проверки

- `tests/unit/invoices.test.ts`: конфигурация, банковская контрольная сумма,
  единицы товара, НДС и сумма прописью, кириллица/многостраничный PDF,
  постоянное хранение и вложение SMTP.
- `tests/unit/api.test.ts`: сохранение PDF, отказ почты/диска/генерации,
  скачивание только с правильным токеном, неизменность файла.
- `tests/unit/checkout.test.ts`: подтверждение заказа и capability в хранилище,
  контракт скачивания и ошибка API.
- `tests/e2e/orders.spec.ts`: кнопка, ошибка и повторное скачивание, reload,
  отказ sessionStorage, обе темы и мобильный экран. Реальные письма не отправляются.

Печатный образец для визуальной проверки:
`output/pdf/rwb-invoice-preview.pdf`. Исходные данные в нём тестовые; состав и
сумма соответствуют четырём позициям ручной проверки корзины. Корзина пользователя
для подготовки образца не изменялась.

Проверка 09.11.2026: 16 unit/API проверок новой функциональности прошли;
8 браузерных сценариев прошли и в production-сборке на 3100, и на dev-сервере
3000. Production-сборка, TypeScript и ESLint прошли. Реальный локальный API
также создал заказ, сохранил PDF и отдал тот же файл по защищённому запросу;
при отсутствии SMTP статус письма корректно остался `FAILED`.
Полный `npm test`: 186 pass, 34 fail, 3 skip. Изолированная копия исходного
коммита дала тот же набор из 34 сбоев; новых сбоев полного набора нет.
Эти исторические проверки не исправлялись в задаче по счетам.
