# Архитектура ООО «РВБ»

## Общая схема

Проект остаётся единым приложением Next.js 16. Отдельный backend не нужен: каталог небольшой, публичные страницы не
зависят от пользовательских данных, а корзина работает в браузере. Большинство страниц формируется статически из
TypeScript-данных. Каталог использует четыре уровня: `Category → Subcategory → ProductType → ProductVariant`.
Карточка представляет `ProductType`, а покупаемая строка таблицы и позиция корзины — конкретный `ProductVariant`.
Только операции, которым нельзя доверять браузер, выполняются в Route Handlers.

`output: "export"` намеренно не включён. Статический хостинг не способен выполнить POST-обработчики заказов, платежей,
webhook и форм. Полностью статическое размещение станет возможно только после передачи всех этих операций внешним
hosted-сервисам.

## Что работает на frontend

- каталог, категории, типы продукции, варианты и статические информационные страницы;
- фильтрация и сортировка типов продукции и вариантов;
- корзина в `localStorage`;
- интерфейс checkout и сбор контактных/доставочных данных.

В `localStorage` сохраняются `productId`, `quantity` и, для расчёта по массе, введённые метры/тонны.
`lib/cart.ts` проверяет записи и оставляет последнее состояние для повторяющегося ID.
Название, актуальная цена и масса берутся из каталога; сохранённые денежные суммы не используются.
Неизвестные ID остаются видимыми с просьбой удалить/уточнить позицию и блокируют checkout.
При недоступном хранилище корзина продолжает работать в памяти вкладки.

## Доверенная серверная граница

- `POST /api/orders` проверяет входные данные, заново находит товары и рассчитывает сумму;
- `POST /api/payments/create` проверяет суммы с округлением каждой строки до копеек; метры пересчитывает в тонны. Платёжный провайдер не настроен;
- `POST /api/payments/webhook` делегирует проверку подписи адаптеру провайдера и только после проверки меняет статус;
- `POST /api/contact` и `POST /api/quote` валидируют формы и возвращают 503, поскольку отправка не настроена.
  Это относится и к разработке: молчаливого «успеха» без доставки больше нет.

Корзина и сервер используют одно правило `lib/cartPricing.ts` и формулы `lib/orderMeasurement.ts`.
Переполнение и некорректное количество не превращаются в допустимый заказ с нулевой стоимостью.

Платёж нельзя безопасно выполнить только на frontend: код и `localStorage` контролирует пользователь, секретный ключ
нельзя отдавать в браузер, а redirect после оплаты не доказывает факт платежа. Поэтому цены пересчитываются из
серверного каталога, а статус `PAID` может прийти только из подписанного webhook.

## Редактирование каталога

Категории находятся в `data/categories.ts`, подкатегории — в `data/subcategories.ts`, Product Types формируются в
`data/productTypes.ts`, а варианты — в `data/products/*.ts` и сохранённом `data/imported-catalog.json`. `data/products/index.ts` нормализует
варианты: добавляет `productTypeId`, unit, availability, material, standard и демонстрационный расчётный вес.
Компоненты получают данные через `lib/catalog.ts`. На момент аудита: 19 категорий, 76 подкатегорий/типов и 675 вариантов.
Подготовка импортированных записей описана в `docs/catalog-import.md`.
Обычные тесты и сборка не запускают импорт и не применяют скидку повторно.

Чтобы изменить цену или описание, откройте файл нужной товарной группы и измените единственное поле `price`,
`shortDescription` или `description` в объекте товара. Цена хранится числом рублей с возможными копейками, например `price: 11111.10`; `null` означает запрос цены. Единица цены хранится отдельно.

Чтобы добавить покупаемый вариант:

1. выберите соответствующий файл в `data/products/`;
2. добавьте полный исходный объект `ProductVariantSource` с уникальными `id`, `slug` и `sku`;
3. укажите существующие `categoryId` и `subcategoryId`;
4. явно заполните цену, единицу, оба описания, наличие, featured-флаг, изображения, attributes и specifications.

Product Type создаётся из соответствующей подкатегории и открывается по каноническому URL
`/catalog/[categorySlug]/[subcategorySlug]/[productTypeSlug]`. Старые URL отдельных товаров перенаправляются на
страницу Product Type и конкретный вариант.

Публичные изображения и явные соответствия описаны в `docs/catalog-images.md`:
`public/images/catalog/`, `data/catalog-images.json`, `data/catalog-image-versions.json`.
Исходные фотографии и данные поставщика не удаляются при очистке кода.

Арматура и балка используют отдельные явные столбцы в `RebarVariantCatalog.tsx` и строки
`MeasuredVariantItem.tsx`; остальные категории сохраняют существующую таблицу характеристик.
`useLinkedVariant` раскрывает строки по ссылкам поиска/корзины на обоих размерах экрана.
`lib/catalogFilters.ts` содержит правила фильтра категории и сортировки неизвестных цен.

## Хранилище и адаптеры

Разработка использует процессное in-memory хранилище заказов; данные исчезают при перезапуске.
Уведомления не настроены в любом окружении, поэтому создание заказа завершается ошибкой отправки,
а корзина сохраняется. Браузерные проверки подменяют HTTP-ответы локально, не отправляя заявки.

В production текущие адаптеры намеренно возвращают ошибку конфигурации. Перед запуском нужно:

- подключить постоянное хранилище, реализовав `OrderRepository`;
- выбрать hosted payment provider и реализовать `PaymentProvider` по официальной спецификации/SDK;
- обеспечить проверку webhook-подписи и постоянную идемпотентность событий;
- реализовать `NotificationService`;
- настроить HTTPS, домен и секреты платформы;
- выполнить сквозные тесты invoice/card/form flows.

## Переменные окружения

Шаблон находится в `.env.example`:

- `NEXT_PUBLIC_SITE_URL` — единственная публичная переменная;
- `PAYMENT_PROVIDER`, `PAYMENT_SECRET_KEY`, `PAYMENT_WEBHOOK_SECRET`;
- `NOTIFICATION_PROVIDER`, `NOTIFICATION_API_KEY`, `NOTIFICATION_RECIPIENT_EMAIL`.

Серверные секреты не должны иметь префикс `NEXT_PUBLIC_`, попадать в git или выводиться в логи.

Переменные провайдеров — шаблон будущего подключения, а не готовая интеграция. Одного их заполнения недостаточно.
