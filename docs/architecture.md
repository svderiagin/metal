# Архитектура ООО «РВБ»

## Общая схема

Проект остаётся единым приложением Next.js 16. Отдельный backend не нужен: каталог небольшой, публичные страницы не
зависят от пользовательских данных, а корзина работает в браузере. Большинство страниц формируется статически из
TypeScript-данных. Каталог использует четыре уровня: `Category → Subcategory → ProductType → ProductVariant`.
Карточка представляет `ProductType`, а покупаемая строка таблицы и позиция корзины — конкретный `ProductVariant`.
Нормативные сведения карточек арматуры заданы в подкатегориях (`materialDescription`, `referenceStandard`).
Характеристики партии подтверждают её документы.
`lib/productTypeSummary.ts` рассчитывает цену карточки по совместимым единицам без неподтверждённых демонстрационных цен (`demo: true`). Явное подтверждение владельцем (`priceConfirmed: true`) разрешает учитывать цену, сохраняя технические атрибуты демозаписи неподтверждёнными.
Подробности проверки и оставшиеся вопросы: `docs/rebar-cards-audit.md`.
Только операции, которым нельзя доверять браузер, выполняются в Route Handlers.

`output: "export"` намеренно не включён. Статический хостинг не способен выполнить POST-обработчики заказов, платежей,
webhook и форм. Полностью статическое размещение станет возможно только после передачи всех этих операций внешним
hosted-сервисам.

## Что работает на frontend

- каталог, категории, типы продукции, варианты и статические информационные страницы;
- фильтрация и сортировка типов продукции и вариантов;
- корзина в `localStorage`;
- интерфейс checkout и сбор контактных/доставочных данных.

В `localStorage` сохраняются `productId`, `quantity` и, для расчёта по массе, введённые метры/тонны.
`lib/cart.ts` проверяет записи и оставляет последнее состояние для повторяющегося ID.
Название, актуальная цена и масса берутся из каталога; сохранённые денежные суммы не используются.
Неизвестные ID остаются видимыми с просьбой удалить/уточнить позицию и блокируют checkout.
При недоступном хранилище корзина продолжает работать в памяти вкладки.

## Доверенная серверная граница

- `POST /api/orders` проверяет входные данные, пересчитывает сумму, сохраняет заказ и формирует счёт при выборе оплаты по счёту;
- `GET /api/orders/[reference]/invoice` отдаёт сохранённый PDF по токену заказа;
- `POST /api/payments/create` проверяет суммы с округлением каждой строки до копеек; метры пересчитывает в тонны. Платёжный провайдер не настроен;
- `POST /api/payments/webhook` делегирует проверку подписи адаптеру провайдера и только после проверки меняет статус;
- `POST /api/contact` и `POST /api/quote` валидируют формы и отправляют сообщения через SMTP. При ошибке отправки возвращают 503.

Корзина и сервер используют одно правило `lib/cartPricing.ts` и формулы `lib/orderMeasurement.ts`.
Переполнение и некорректное количество не превращаются в допустимый заказ с нулевой стоимостью.

Платёж нельзя безопасно выполнить только на frontend: код и `localStorage` контролирует пользователь, секретный ключ
нельзя отдавать в браузер, а redirect после оплаты не доказывает факт платежа. Поэтому цены пересчитываются из
серверного каталога, а статус `PAID` может прийти только из подписанного webhook.

## Редактирование каталога

Категории находятся в `data/categories.ts`, подкатегории — в `data/subcategories.ts`, Product Types формируются в
`data/productTypes.ts`, а варианты — в `data/products/*.ts` и локальных наборах `data/catalog-positions.json` и `data/additional-catalog.json`. `data/products/index.ts` нормализует
варианты: добавляет `productTypeId`, unit, availability, material, standard и демонстрационный расчётный вес.
Компоненты получают данные через `lib/catalog.ts`. Для актуального количества категорий и вариантов запустите
`node .agents/skills/metal-frontend-catalog/scripts/catalog_state.mjs --summary`.
Категория «Труба круглая» (`cat-trk`, `/catalog/truba-kruglaya`) идёт после профильных труб.
В неё перенесены водогазопроводная и электросварная подкатегории с сохранением их ID;
оцинкованные исполнения выделены в `cat-trk-sub-3` и `cat-trk-sub-4`. Остальные стальные трубы сохраняют прежнюю категорию.
Локальные варианты круглых труб хранятся в `data/products/trubaKruglayaLegacy.ts`.
Хранение и обновление товарных данных описаны в [структуре каталога](catalog-data.md).
Перед сборкой регенерируются проекция корзины, версии изображений и адаптивные фотографии.
Архивные MS-0071/MS-0072 отфильтровываются через `data/catalog-visibility.ts`; исходные объекты сохранены.
Трубы не используют демонстрационную оценку массы: см. `lib/pipeWeight.ts` и [аудит ВГП](vgp-audit.md).

Цену и описания меняйте в исходной записи нужной товарной группы. Цена хранится в рублях
с возможными копейками. Для позиций с расчётом в тоннах сверяйте поля `price` и `pricePerTon`,
единицу и условия оформления. После правки обновите проекцию командой `node scripts/cart-catalog.mjs`.

Чтобы добавить покупаемый вариант:

1. выберите соответствующий файл в `data/products/`;
2. добавьте полный исходный объект `ProductVariantSource` с уникальными `id`, `slug` и `sku`;
3. укажите существующие `categoryId` и `subcategoryId`;
4. явно заполните цену, единицу, оба описания, наличие, featured-флаг, изображения, attributes и specifications.

Product Type создаётся из соответствующей подкатегории и открывается по каноническому URL
`/catalog/[categorySlug]/[subcategorySlug]/[productTypeSlug]`. Старые URL отдельных товаров перенаправляются на
страницу Product Type и конкретный вариант.

Публичные изображения и явные соответствия описаны в `docs/catalog-images.md`:
`public/images/catalog/`, `data/catalog-images.json`, `data/catalog-image-versions.json`.
Готовая разметка лежит в `measurement/`, фотографии для галереи в `cover/`, исходники в `originals/`.

`ProductVariantCatalog.tsx` выбирает таблицу для семейства. Арматура, балки, ВГП, электросварные
и профильные трубы используют конфигурации из `RebarVariantCatalog.tsx`. Для других семейств
используются отдельные таблицы сетки и профнастила или `GenericProductVariantCatalog.tsx`.
Все блоки фильтров используют общую разметку `FilterPanel.tsx`; наборы полей и обработчики остаются в компонентах каталога.
`lib/profilePipe.ts` проверяет количество и длину. Для поштучного режима `CartItem.pieceOrder`
сохраняет число труб и длину одной трубы. Для измеряемого заказа `CartItem.measurement` хранит режим
ввода и рассчитанные метры и тонны. Применимый режим зависит от данных позиции.
Для ВГП `lib/vgp.ts` округляет запрос в метрах или тоннах вверх до целых труб указанной длины.
Стоимость считается по табличной массе без округления промежуточного веса. `lib/cartPricing.ts`
проверяет кратность длины и на клиенте, и при создании серверного заказа. Старые строки ВГП
без измерений или с дробной длиной требуют явного обновления через таблицу товара.
`useLinkedVariant` раскрывает строки по ссылкам поиска и корзины. Старые идентификаторы распознаёт
`lib/catalogIdentity.ts`. Категории с прямыми позициями показывают таблицу на странице категории.
`lib/catalogFilters.ts` содержит сравнение цен с размещением неизвестных значений в конце списка.

## Хранилище и адаптеры

Локальная разработка хранит заказы в `.local/orders`. Развёрнутое приложение использует
`ORDER_STORAGE_DIR` для файлового хранилища или `ORDER_DATABASE_URL` для PostgreSQL.
SMTP отправляет письма по заказам и сообщения из форм. Ошибка отправки письма по заказу
фиксируется отдельно от результата сохранения заказа.

Настройка хранилища, SMTP и счетов описана в [развёртывании](deployment.md)
и [генерации счетов](invoice-generation.md). Адаптер оплаты картой пока возвращает ошибку конфигурации.
Проверку форм проводите с локальной подменой ответов, когда отправка писем не входит в задачу.

## Переменные окружения

Шаблон находится в `.env.example`:

- `NEXT_PUBLIC_SITE_URL` задаёт публичный адрес витрины.
- `ORDER_STORAGE_DIR` или `ORDER_DATABASE_URL` задают хранилище заказов.
- `SMTP_*` и `NOTIFICATION_RECIPIENT_EMAIL` настраивают отправку сообщений.
- `INVOICE_*` задают режим, реквизиты и параметры счёта.
- `PAYMENT_*` оставлены для будущего адаптера оплаты.

Серверные секреты не должны иметь префикс `NEXT_PUBLIC_`, попадать в git или выводиться в логи.
