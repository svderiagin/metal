# Разработка: короткий маршрут

Работайте из корня репозитория. `package.json` требует Node 22.x; сверяйте `node --version` при проблемах окружения. Используйте установленный lockfile, не обновляйте зависимости для обычной правки.

## Выбор файлов

1. `git status --short`, затем поиск `rg` по названию компонента, slug или ID.
2. Прочитайте ближайший компонент и его helper/тип. Большие JSON исследуйте программно по ID с выводом выбранных полей.
3. Для изменений каталога получите текущие счётчики: `node .agents/skills/metal-frontend-catalog/scripts/catalog_state.mjs --summary`. Без флага выводится разбивка по категориям. Скрипт не проверяет хеши изображений и всю семантику маршрутов.
4. Перед кодом Next.js найдите соответствующий локальный guide в `node_modules/next/dist/docs/`; не переносите API из памяти о старых версиях.

## Проверки по масштабу

| Изменение | Достаточная исходная проверка |
| --- | --- |
| Только инструкции/документация | Ссылки, команды, валидация изменённых навыков. Сборка приложения не нужна. |
| Текст, CSS, локальная вёрстка | ESLint затронутых файлов, браузер затронутой страницы; TypeScript при изменении TS/TSX. |
| Фото, иллюстрации и подписи на изображениях | [Визуальная проверка по исходнику](catalog-images.md#image-quality-review-required), тесты изображений затронутого семейства и обновлённые URL версий; ESLint при правках генератора. |
| Поведение компонента или данные | Существующий тест области, TypeScript, ESLint. Проверить нормальное и пограничное состояние. |
| Общие типы, маршруты, каталог, цены/заказ или изменения нескольких областей | После локальных проверок один раз `npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`. |

Фокусный запуск: `node --test scripts/<area>.test.mjs`. Для диагностики без изменения TypeScript-кэша: `npx tsc --noEmit --incremental false`.

Новые тесты TypeScript: `node --import tsx --test tests/unit/<area>.test.ts`.
Для широкого аудита без генерации данных используйте `npm run test:unit` вместо
`npm test`; production-сборка для браузерных тестов — `npm run test:build`
в отдельном `.next-test`. Тесты браузера и эталоны запускаются последовательно
на 3100, не затрагивая dev-сервер 3000. Команды, пороги покрытия и правила PNG:
[testing.md](testing.md). Для инфраструктуры проверок подключайте
`metal-frontend-quality`; для обычной правки достаточно навыка области.

Повторяйте проверку после значимых для неё изменений, а не после каждого редактирования. Новые тесты нужны для поведения/регрессий, а не для буквального порядка JSX или совпадения текста инструкции. Исходные сбои фиксируйте отдельно; не обновляйте эталоны ради зелёного результата.

### Локальные задачи по интерфейсу и изображениям

Перед реализацией определите затронутый компонент, его потребителей и необходимые
доказательства качества. Выберите существующие фокусные тесты и скриншоты;
добавляйте сценарии для нового поведения или найденной регрессии. После первого
рабочего варианта проверьте его на dev-сервере, чтобы рано заметить ошибки UX.
Затем завершите правки и выполните согласованный набор проверок.

- Переиспользуйте `tests/browser.ts`, существующие fixtures, настройку viewport,
  темы и ожидания загрузки шрифтов/изображений. Состояния, которых пока нет
  в данных каталога (например, несколько кадров будущей галереи), проверяйте
  изолированно с настоящим компонентом, сохраняя реальные данные сайта.
  Новый стенд или отдельный сборщик оправдан, когда существующее окружение
  не позволяет проверить существенное поведение. При повторных сбоях настройки
  стенда отделите проблему окружения от дефекта приложения и пересмотрите способ
  проверки; сохраните проверку самого поведения.
- Когда нужна production-проверка, собирайте актуальное приложение после
  завершения правок. Изменения только тестов и документации не требуют пересборки.
  После исправления ошибки повторяйте упавший сценарий и проверки, чьи результаты
  могли стать неактуальными. Полный E2E/визуальный набор используйте при широком
  влиянии, изменении общих контрактов или явном требовании задачи/CI;
  локальная UI-правка сама по себе не требует всех наборов приложения.
- Визуально проверяйте результат на desktop и mobile, в затронутых темах;
  320 px и границы переключения раскладки добавляйте при риске тесных контролов
  или изменения геометрии. Для фото смотрите реальную миниатюру и увеличенный
  кадр: пропорции, обрезку, резкость, края и читаемость подписей. При изменении
  самих изображений сохраняется полный [контроль по исходнику](catalog-images.md#image-quality-review-required),
  включая производный вариант и фрагменты текста при 1:1.
- Для изменений просмотра фото выбирайте соответствующие проверки: открытие
  и закрытие, клавиатура и возврат фокуса, блокировка/возврат прокрутки,
  вписывание в экран, масштаб 1:1 и перемещение, ошибка загрузки.
  Изменения галереи требуют проверки нескольких кадров, стрелок, порядка
  и перехода через границу списка. При изменении раскладки контролируйте также
  соседние блоки: фильтры, каталог, таблицы. Не распространяйте этот список
  на задачи, которые не затрагивают соответствующее поведение.
- При расхождении скриншотов изучайте actual/diff. Обновляйте только проверенные
  намеренные изменения, затем повторно сравнивайте новые/изменённые снимки
  без обновления эталонов. Остальные уже прошедшие сравнения повторяйте,
  когда новые правки могут повлиять на них. Сохраняйте доказательный скриншот
  результата для отчёта пользователю.

Завершайте задачу, когда выбранные проверки прошли, изображения и интерфейс
просмотрены, а найденные существенные дефекты исправлены либо явно описаны.
Дополнительный полный прогон требует причины: новая правка, сбой или
непроверенный риск. Этот порядок сокращает повторную настройку и запуски,
сохраняя визуальный контроль качества.

## Генерируемые файлы

- `data/cart-catalog.json` — проекция публичного каталога для клиента; её читает `lib/cartCatalog.ts`. Не редактировать как независимый прайс. После изменения исходных цен/товаров: `node scripts/cart-catalog.mjs` перед проверкой корзины.
- `data/catalog-image-versions.json` — хеши локальных файлов. `node scripts/catalog-image-versions.mjs` обновляет **и хеши, и проекцию корзины**.
- `npm run dev` запускает этот генератор и наблюдение за исходниками; `npm test` и `npm run build` также имеют генерирующие pre-хуки. Прямой `node --test ...` pre-хук не вызывает.
- Импорт Brokinvest (`npm run catalog:import`) и Rozmet (`node scripts/import-rozmet.mjs`) перезаписывает данные. Запускайте только в задаче на импорт; до запуска учитывайте ручные правки и overlays. Не регенерируйте каталог как способ исправить тест.
- После команд с генерацией проверяйте `git diff --stat` и конкретный diff. При аудите предпочтителен прямой запуск тестов без pre-хука, с явным указанием этого в отчёте.

## Локальный браузер

Переиспользуйте работающий сервер на `http://127.0.0.1:3000`. Для проверки создайте отдельную вкладку. Проверяйте целевой маршрут и одно значимое пограничное состояние. Для адаптивных правок: desktop и 390 px; 320 px — если меняются тесные контролы. После навигации дождитесь готового интерфейса: начальное disabled до гидратации не доказывает ошибку.

Для изменений темы проверяйте светлый и тёмный режимы; сохраняйте исходный выбор пользователя. Проверяйте фокус/клавиатуру при изменении меню, диалога или формы. Не очищайте пользовательскую корзину ради теста. Формы проверяйте без реальной доставки, если отправка не входит в задачу.

Существующие `scripts/check-*-browser.mjs` используют прямой CDP и исторические селекторы. Они не являются обязательным smoke-тестом. При доступном инструменте управления браузером следуйте его правилам; не запускайте CDP-обход параллельно. Результаты старых performance-аудитов не заменяют текущие production-замеры.
