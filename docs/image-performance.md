# Загрузка фотографий: локальная проверка 16.10.2026

## Среда и границы проверки

Next.js 16.2.11, React 19.2.4, Node.js 25.9.0, Chrome 155. Приложение собирается и запускается
как Node Web Service (`next build` / `next start`), не как static export. В репозитории нет
App Platform app spec или Dockerfile; публичный адрес и настройки удалённого приложения не предоставлены.
DigitalOcean, TLS, CDN, региональная задержка и загрузка процессора удалённого инстанса не измерялись.
В `package.json` сохранено требование Node 22.x; отдельная проверка на Node 22 не выполнялась.

До изменений сохранена отдельная production-сборка, затем проверена окончательная сборка.
Страницы: `/`, `/catalog`, `/catalog/armatura`, страница А500С и страница стального швеллера.
Viewport: 1440×1000, DPR 1 и 390×844, DPR 2. CDP: 1,6 Мбит/с download, 750 Кбит/с upload,
latency 150 мс, замедление CPU ×4. По три холодных прогона каждого сочетания; медианы.
Для холодных прогонов очищался HTTP-кэш отдельного Chrome и кэш оптимизатора **только копии сборки**.
Тёплый прогон измерялся отдельно после посещения той же страницы с включённым кэшем.
Начальное окно — около 8 секунд без действий пользователя; карусель работает естественным образом.

Сырые данные, URL, инициаторы, приоритеты, заголовки, Resource Timing, LCP, CLS, long tasks,
размеры изображений и снимки находятся в `.tmp/image-performance/` и не входят в Git.
`before/measurements.json` — исходная версия, `after-final/measurements.json` — окончательная.
Первый промежуточный эксперимент `after/` не используется для итогового сравнения.

## Подтверждённые причины

- Первый герой уже обнаруживался парсером примерно через 170 мс, с высоким приоритетом.
  Задержку обнаружения дополнительный preload не исправил бы. `HeroCarousel` держал все фотографии
  с `opacity: 0`, пока клиентский обработчик не завершал `decode()` и не обновлял состояние.
  В dev снимок закончил загружаться на 2230 мс, но впервые появился только на 8160 мс.
  Это ожидание гидратации и отображения, а не восьмисекундная передача файла.
- Браузер получает AVIF из `/_next/image`, а не исходные JPEG по 1–1,3 МБ.
  На desktop первый герой запрашивался шириной 1920 при отображении около 1425 px;
  карточки шириной 317–419 px часто получали вариант 640 px. Одновременно нативная lazy-загрузка
  начинала несколько запросов карточек ниже экрана. Это заметная конкуренция за ограниченный канал.
- Ожидание первого ответа оптимизатора есть при холодном серверном кэше. Оно отделено в сетевых
  записях от скачивания и последующего показа. Переход на другой формат без измерений не применялся.
- Общий `app/loading.tsx` создавал короткую заглушку, за которой был виден футер. После появления
  настоящей страницы футер смещался; холодный CLS на desktop достигал 0,458. Это не изменение
  размеров уже загруженной фотографии.
- Исходные `/images/...` обслуживает Next.js из `public`; до изменений у них был `max-age=0`.
  Оптимизированные ответы имели `max-age=14400, must-revalidate`. URL каталога и героя уже содержат
  SHA-256-хеш содержимого в `v`, поэтому для этих адресов возможно длительное кэширование.

Главная в production передавала примерно 258 КБ JavaScript за окно наблюдения; в dev — 864 КБ.
Профилирование не показало необходимости менять каталог, API или архитектуру ради фотографий.
Связь первого кадра с готовностью JavaScript устранена непосредственно в карусели.

## Изменения

- `components/home/HeroCarousel.tsx`: первый пригодный кадр активен уже в серверном HTML.
  Декодирование по-прежнему проверяется перед последующими переходами. Подготавливается один
  следующий кадр; невидимый блок и скрытая вкладка не продолжают запрашивать остальные снимки.
  Переходы, стрелки, свайпы, паузы, обработка ошибок и reduced motion сохранены.
- `CategoryCard.tsx`, `ProductTypeCard.tsx`, `CatalogImage.tsx`: нативный `sizes="auto, ..."`
  у lazy-изображений выбирает вариант по фактическому размеру. Медиаусловия оставлены как fallback.
  Это предусмотрено [стандартом HTML](https://html.spec.whatwg.org/multipage/images.html#sizes-attributes).
  Размеры зарезервированы прежними контейнерами; обрезка и позиционирование не изменены.
- `next.config.ts`: добавлены ширины 1440, 320 и 480; AVIF/WebP и качество сохранены.
  Годовой immutable-кэш применяется к исходным `/images/...` только при наличии 12-значного
  шестнадцатеричного `v`. Адреса без версии остаются с прежним безопасным кэшем.
- `app/loading.tsx`: заглушка резервирует высоту экрана, чтобы футер не появлялся и не уезжал
  при начальной загрузке. Готовые страницы и панели фильтров не изменены.
- `scripts/hero-loading.test.mjs`: проверка настоящего серверного рендера до выполнения effects.
  `scripts/check-local-browser.mjs` учитывает подготовку только следующего кадра при reduced motion.
  `scripts/measure-images.mjs` сохраняет воспроизводимые сетевые и браузерные измерения.

Исходные фотографии, соответствия изображений товарам, тексты, цены и маршруты не изменялись.
Новые локальные материалы пользователя и подготовленные ранее файлы профильных труб сохранены.

| --- | --- | --- | --- | --- |
| Главная, desktop | 5,548 → 3,832 с | 13 → 13 | 948 → 630 | 0,458 → 0 |
| Главная, mobile | 2,864 → 2,152 с | 9 → 7 | 528 → 412 | 0 → 0 |
| Каталог, desktop | 2,588 → 2,016 с | 12 → 12 | 516 → 239 | 0,4615 → 0,0035 |
| Арматура, desktop | 1,512 → 1,504 с | 6 → 6 | 139 → 61 | 0,458 → 0 |

| Швеллер, desktop | 1,328 → 1,316 с | 3 → 3 | 5 → 5 | 0,458 → 0 |

На главной первый показ основного снимка по Element Timing совпал с указанным LCP.
В мобильных страницах каталога и товаров фотографии находились вне первого экрана;
нулевое/отсутствующее время их первого показа не трактуется как ускорение. Их загрузка после прокрутки проверена отдельно.
Тёплый LCP главной: desktop 656 → 296 мс, mobile 696 → 320 мс; передача изображений — 0 байт в обеих версиях.

Фактически доставленные AVIF: герой desktop 1920×1280 / 218509 байт → 1440×960 / 150178 байт;
карточка А500С в категории 640×320 / 47209 байт → 320×160 / 12567 байт.
Исходные файлы сохранены. Проверка HTTP подтвердила `immutable` только для корректно оформленного `v`;
без `v` и с `v=invalid` остался `public, max-age=0`.

Успешны production-сборка, 90 тестов (3 штатных пропуска), проверка ESLint изменённых компонентов и инструментов.
Отдельная браузерная проверка: 60 сценариев, 280 отображений изображений, без ошибок;
включены все категории, размеры 320/390/768/1440, показ без внешнего JavaScript,
reduced motion, ручной переход, подготовка следующего кадра и остановка запросов вне экрана.
Полный прежний `check-local-browser.mjs` после этих изменений не запускался.
Отдельное CPU-время декодирования не измерялось: зафиксированы окончание передачи и фактический показ,
а не предполагаемая длительность декодера. Удалённая production-среда остаётся непроверенной.

## Повторение измерений

Нужен отдельный Chrome с CDP (по умолчанию `127.0.0.1:9225`), не повседневный профиль браузера:
холодные прогоны очищают его HTTP-кэш. Проверка только читает страницы, не отправляет формы/API.

```sh
npm run build
npm run start -- --hostname 127.0.0.1 --port 3102
PERF_URL=http://127.0.0.1:3102 PERF_LABEL=verification node scripts/measure-images.mjs
```

`PERF_RUNS`, `PERF_PAGES`, `PERF_PROFILE` (`desktop` / `mobile`) и `AUDIT_CDP` переопределяют параметры.
Без `PERF_COLD_IMAGE_CACHE` очищается только браузерный кэш. Для повторения именно холодного
оптимизатора используйте сохранённую отдельную копию `.next` и, например,
`PERF_COLD_IMAGE_CACHE=.tmp/image-performance/final-app/.next/cache/images`.
Скрипт запрещает удалять кэш вне этой временной папки. `PERF_TRACE=1` дополнительно записывает trace Chrome.

Отдельная подготовка или повторное сжатие фотографий не требуется: варианты создаёт существующий
оптимизатор Next.js. Обычный `npm run build` обновляет хеши через существующий `prebuild`.
Деплой и настройки DigitalOcean в этой задаче не менялись. Для применения на сервере нужна обычная
сборка и публикация владельцем; новые сервисы или настройки DNS не требуются.
